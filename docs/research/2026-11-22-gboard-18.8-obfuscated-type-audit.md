# Gboard 18.8: obfuscated-type audit of the extensions and injected smali

Date: 2026-11-22 · Bundles built against 18.8.0.1022711984-beta (176124766 / 176124765)

## Why

The access-point `VerifyError` (`Lwim;` cast in a method whose parameter is `Lauco;`) showed that a
stale obfuscated type is invisible to `ValidateDex`: the name still exists in 18.8 as a *different*
class, so existence checks and patching both succeed and only ART fails, at runtime, taking every
feature that depends on the class with it.

## Tools

- `scripts/audit-obfuscated-types.py` — scans every `Class.forName("x")` literal in the Gboard
  extensions and every type descriptor in injected smali, and compares with the 18.6.3 → 18.8
  class map. It reports **ERROR** only when the literal is provably stale (the 18.6.3 class no
  longer exists in 18.8 and the mapped class does) and **WARN** when the name is reused (18.6.3
  `aagb` is also a valid 18.8 class, so only a member-level check can decide).
- `scripts/EmittedParameterCasts.java` — dexlib2 dumper that, for every method in a patched APK
  containing a runtime-extension reference, reports `CHECK_CAST` on a parameter register whose type
  differs from the declaration. Run it per build; the *difference* between two builds is the
  signal, because normal code has legitimate downcasts.

## What it found

- 70 reflection literals in the Gboard extensions; **18 pointed at classes that do not exist in
  18.8**. They are now mapped (e.g. `zxo`→`bajd`, `lyu`→`zgp`, `srk`→`amly`, `aatf`→`bcqz`,
  `mbb`→`zkd`, `nng`→`acbl`). The OCR path (`GboardOcrRuntime`, `GboardOcrModuleInstaller`,
  `GboardOcrBundledBridge`) accounted for 9 of them, so Scan Text was resolving nothing before.
- 4 literals in patch sources named classes absent from 18.8: `Lqll;`→`Lahpe;`, `Lqnm;`→`Lahsz;`,
  `Lwyw;`→`Lauys;`, `Lwyz;`→`Lauzc;` (12 sites).
- 6 remaining provably-stale literals are tracked in the script's `KNOWN_STALE` set:
  `accesspointsmenu` (`Lnpq;`, `Lqnp;`), `writingtools` (`Lwgv;`) and `advancedvoice`
  (`Ltdn;`, `Lltr;`, `Lwdm;`). Those need member-level resolution, not a rename; the tool keeps
  them visible and fails on any *new* one.
- 129 literals are ambiguous (name reused); the bindings' `Validate` covers the patch targets,
  the extensions still need a member-level pass.
