# Maps native car overlay investigation

Target: Google Maps 26.43.05.1002020710 (1068844719), universal APK SHA-256 `81506a2c54fc9a8faca34c18af7619d9c9d26cbfbe799b66884a59ac17791004`. These are static observations, not evidence of on-device behavior.

The requested result is a full-surface map with controls avoiding measured host overlays, including the space below a compact card. The current adapter receives CAL visible/stable rectangles but discards them. DriveDeck's `ChromeCover.visibleWithin` reduces each cover to an edge inset, so its reported rectangle cannot reconstruct a floating card's lower edge. A separate versioned host/adapter geometry contract is needed for precise placement.

## Native inset path

In this exact APK, `DrawingSpec.toString()` identifies its `Rect e` as `systemWindowInsets` (REA evidence `ev_020176e37725be6e905f2b6920b7aaa2ea804de0885e479341172fdf10b75f54`). It represents four edge insets, not the coordinates of a visible rectangle. `bemm.q(DrawingSpec)` copies that rect into `v` and forwards it to the presentation's `r` method (REA `ev_0a9b3738ca0551cb6d67600f00d36453dbb10ad5a12425dfc3f6153e58571d52`). In the `bemz` presentation, `r` calls `bejn.t`, which copies it into `F`. `beji.onApplyWindowInsets` uses `F` to replace system window insets for the native view hierarchy. `bemz.A` additionally requests inset application on the presentation view; calling `q` alone does not explicitly request it. The other presentation implementation and the feature flag selecting inset dispatch must also be examined before selecting a hook.

This establishes a candidate path for edge insets, not that Maps controls alone move while map pixels remain full-surface. The native view hierarchy could also apply those insets to the map or other content. It cannot encode an L-shaped safe area or a floating card's lower edge. Do not insert an unconverted CAL visible rectangle into `DrawingSpec`, and do not claim this path meets the overlay requirement without rendered-frame and real hit-test evidence.

The Android 16 alternate `benc` presentation also stores edge insets and its `A(Rect)` requests inset application; its listener in `tof` supplies those values as system bars. That presentation's setup additionally requires an input transfer token, so it cannot be substituted for the existing virtual-display path without proving its prerequisites.

## Native control ownership

Static JADX output identifies `rcq` as `MapButtonsController`. It locates `map_buttons_view_container`, the compass, mute, microphone, settings and report containers, plus `zoom_widget_view`. `rdx` constructs the one-bar container and its child controls, while `ref` constructs the zoom controls and separate zoom touch-target views. `rcq.d()` installs `TouchDelegate` instances in one mode. Consequently, moving only visible button artwork would not establish correct hit testing; any layout intervention must preserve or recompute the actual target hierarchy and survive Maps' own updates. The full control tree, its dynamic layout rules and the separate recenter and route overlays remain to be traced.

## Baseline and outstanding work

### Implementation in progress

`ProjectionRenderer` now copies visible/stable area updates, clips them to the surface coordinate system, converts visible bounds (or stable bounds when visible is unknown) to edge insets and applies them through `bemz.A(Rect)`. The patch checks the added private `bemm.v` field and `bemz.A` signature before editing an APK. The drawing dimensions remain the original surface dimensions. Repeated equal updates are skipped; resize clears cached geometry, same-canvas target replacement retains it, and close releases the cached areas. This is the safe-rectangle fallback described in the handoff. It does not implement the richer floating-card placement contract or prove that native inset consumers keep map pixels behind overlays.

Area callback rejection now reads the completion callback before checking the captured session/UID, so a rejected request can receive its error. Authorization remains before dispatch, and queued work rechecks session ownership on the main thread.

Validation so far: all 50 Maps extension unit tests pass, including six new area tests and two new capability tests. The patch bundle builds and patch tests pass. The final-source FULL patching run on the supplied APK applied `Native navigation for Gearslip and Android Auto`, reported no failed patches and passed emitted-reference/signature checks. Its bundle digest is `f2a8411c562034afddf82c2387599c04bbccc307b6403a91b26d919cdca62a7c`; the validation APK digest is `c00839ed68f4d1c767402bbbba7ba36d569c664412775692d34b71f7aea02400`. These checks establish patch emission, not runtime behavior. The renderer probe now accepts width/height/DPI and an `areas` action, capturing native control bounds and frames before/after/restoration and checking that the native activity survives the updates. The probe compiles; it has not yet been run on the emitted APK.

Remaining acceptance includes emitted-APK runtime layout/hit testing, independent camera/chrome behavior, precise compact/expanded measured overlay geometry and physical-head-unit validation. No release or main promotion has been performed.

### Measured placement work

`ControlPlacement` now provides a tested surface-pixel planner: it subtracts measured cover rectangles, prefers two columns below the actual player when all targets fit, otherwise selects uncovered space, preserves target sizes and reserves a final overflow target if needed. Seven placement tests cover both sides, expanded cards, additional overlays, larger targets, short available space and a fully covered canvas. All 57 extension unit tests pass. This planner is not yet connected to native layout or exposed by a host transport; its tests must not be claimed as rendered grid or overflow acceptance. The validation APK digest above predates this planner addition and remains evidence for the inset fallback only.

The live hierarchy inventory confirms `map_buttons_view_container` is a `LinearLayout` under `uww`, with a `pcc` ellipsizing group and a separate `one_bar_bottom_group`. Zoom visuals are `AppCompatImageView`s while distinct target views own their delegates. The complete trace is retained as `hierarchy-1280x480.txt`. The next integration must move or lay out those relationships together and preserve native ownership across replacement. A versioned companion transport design, surface-generation rules and the remaining native integration steps are recorded in `docs/design/maps-surface-occlusion-v1.md`.

### Compact native reflow implemented

`NativeControlLayout` now uses the planner to reflow Maps' two intact native control groups below a fitting compact card. It preserves their native parents, handlers and touch delegates, changes only their layout parameters and translation, and disables clipping along the old constrained ancestor chain while active. The renderer routes taps inside the moved group through that group's real native `dispatchTouchEvent`. Clear, close and surface replacement restore original layout/clipping. Unsupported layouts restore the native safe-rectangle fallback. Surface generations still gate companion updates.
